## 1. 项目全景

### 1.1 产品定位

面向中国劳动者的**权益导航与办事平台**：把"该做什么、能拿什么、去哪办"做成一条条可执行的清单与教程，每条指到官方入口；收入 / 个税 / 社保 / 补偿的测算是其中一件工具，AI 只做辅助。完整定位见 `docs/POSITIONING.md`。

> 本报告初稿把产品描述为"灵活就业者的收入测算工具"，是把手段当成了目的。数据与工程结论仍然成立，但首页、导航、AI 提示词的现状与目标定位存在明显偏差，见 4.0。

### 1.2 架构分层

```
Web (Vue 3 + Pinia) ─┐
Desktop (Tauri 2) ───┤
CLI ─────────────────┼──→ application/ScenarioService ──→ domain/{income,tax,benefit,compensation}
HTTP API ────────────┤                                        ↑
MCP ─────────────────┘                                  adapters（元↔分、规则归一）
                                                        kernel/calculate（CLI/API/MCP 唯一入口 + 默认值）
```

- `domain/*` 是纯函数层：金额一律用「分」的整数、单位用 branded type、错误用 `Result<T,E>` 而不是抛异常。
- `application/*` 负责编排与输入校验；`ScenarioService` 是 Web 与 CLI/API/MCP 的共同计算路径。
- `kernel/calculate` 负责默认值合并、规则加载、输出扁平化，是 CLI/API/MCP 的唯一入口；Web store 直接调 `ScenarioService`，两者由 `verify:entrypoints` 做数值对账。
- `src/engine/*` 是迁移期保留的旧引擎，与 `domain/*` 并存，由 parity 测试锁定一致性（见 4.4）。

- 34 座城市规则，309 条来源记录：**official 105 / derived 37 / unverified 167**（官方占 34.0%）。
- 个税表、个体户增值税：34/34 官方核实。

## 3. 本轮开发：修复的 5 个缺陷 + 1 个诚实性改进

> 原则：每个修复都先写探针复现、再改代码、再补回归测试；所有测试与门禁重跑通过。

### 3.1 收入波动模型口径错误（影响最大）

**现象**：总览页「收入波动」卡片里，「收入不够覆盖成本的月份占比」几乎永远是 `0.0%`；「建议应急储备」在默认广州参数下给出 **¥22,734**。

**根因**：`DashboardView` 把当前方案的**月净收入**（6,843.70）当作分布均值的"收入"，同时又传固定成本（1,950）给模拟器。净收入是已经扣过成本的数，恒为正：

1. `belowCostMonthRatio` 比较的是「净收入 < 固定成本」——在任何一个能活下去的方案里都不可能成立，指标结构性失效；
2. `recommendBuffer` 把固定成本同时算进「3 个月支出」和「最差月份缺口」，重复计了一遍。

**修复**：

- `simulateIncomeDistribution` 改为以**月毛收入**为均值做乘性波动，逐月扣除固定支出后输出净收入分位（均值 / P10–P90 / 极值都可能为负）；
- 生存线按「毛收入 < 固定支出」判定，即净收入为负的月份；
- 储备公式改为 `3 个月固定支出 + 3 个月最差月份亏损补足`，不再把成本重复计入；
- 总览页改传 `best.income.grossIncome`，并把文案改成"以月毛收入为均值、逐月扣固定成本"。

**复现证据（默认广州，未参保）**：

| 口径 | 毛收入 | 固定成本 | 净收入 | P10 净收入 | 生存线占比 | 建议储备 |
|---|---:|---:|---:|---:|---:|---:|
| 修复前 | 8,856.25 | 1,950 | 6,843.70 | 3,165.86 | 0.0% | **22,734** |
| 修复后 | 8,856.25 | 1,950 | 6,843.70 | 4,670.30 | 0.0% | **5,850** |

储备建议此前高估 **3.89 倍**。低毛利场景（毛收入 4,200 / 成本 3,000 / CV 50%）下，修复后 P10 净收入 **-975**、生存线占比 **33.6%**，修复前该指标同样失真。

**回归测试**（+5）：分位数整体平移固定支出、生存线按毛收入判定、P10 为正时储备只含 3 个月支出、P10 为负时补足亏损、毛收入为 0 时净收入为 `-成本`。

### 3.2 社保 vs 自助养老的领取年限错配

**现象**：退休年龄从 60 岁改到 50 或 65 岁时，"同样月缴 1,500 元，自己存 vs 交社保"的结论会明显偏向自助。

**根因**：`calcSelfFunded` 未显式传 `payoutYears` 时固定按 **60 岁（23 年）**摊还；社保侧却按用户填的退休年龄计算预期余命。50 岁退休时社保按 30 年、自助仍按 23 年，自助的月领取额被抬高、现值被高估。

**修复**：`compareSocialVsSelf` 默认使用 `expectedPensionYears(socialInput.retireAge)`，显式传参时仍优先。

**复现证据**（月投 1,500、25 年、4% 年化）：

| 退休年龄 | 旧口径月领取（固定 23 年） | 同口径月领取 | 偏差 |
|---|---:|---:|---:|
| 50 岁 | 3,415 | 2,789 | 高估 22% |
| 60 岁 | 3,415 | 3,415 | 无 |
| 65 岁 | 3,415 | 3,984 | 低估 14% |

**回归测试**（+3）：50/55/60/65/70 五档年限、显式传参优先、`coversLifeExpectancy` 同口径。

### 3.3 「多跑2小时」在工时封顶后名不符实

**现象**：左侧工时滑块上限是 14 小时。用户已经拉到 14h 时，方案对比里仍有一张「多跑2小时」卡片，但实际一小时都没多，单量还可能低于当前。

**根因**：`hoursCap = min(dailyHours + 2, 14)`，名称却写死为「多跑2小时」。

**修复**：`hoursCap` 没有增量时，名称改为 `按14小时产能校准`，如实说明这是产能校准而非加时。

**回归测试**（+2）：10h 时保留「多跑2小时」且确实 12h；14h 时不得出现「多跑2小时」。

### 3.4 0 天出勤被算出一个不存在的「有效时薪」

**现象**：本月出勤 0 天时，结果页提示「有效时薪 ¥-1,950.00，低于当地非全日制最低时薪」。

**根因**：时薪校验用 `max(1, dailyHours × workDaysMonth)` 当分母。0 天时净收入是 `-成本`（成本照付，这是对的），却被除成一个月薪式数字，再和最低工资比较。

**修复**：只有 `workedHours > 0` 才做时薪比较；无工时即无时薪。

**回归测试**（+1）：0 天出勤时 `netHourly = 0`、`netMonthly < 0`、不出现「有效时薪」字样。

### 3.5 峰时时段解析丢失分钟与跨零点时段的补贴

**现象**：规则里若出现 `07:45-09:15`（1.5 小时），会被算成 2 小时；若出现夜宵峰时 `22:00-02:00`（4 小时），会被算成 0——补贴被静默抹掉。

**根因**：旧实现只取字符串前两位的 `HH`，且 `end <= start` 直接记 0。

**修复**：按 `HH:MM` 解析到分钟；跨零点视为次日；非法格式（`25:00`、`24:30`、`10:60`）忽略；整 24 小时与零长度不计。

**回归测试**（+4）：`07:45-09:15 = 1.5h`、`22:00-02:00 = 4h`、`22:00-24:00 = 2h`、非法时刻为 0。当前 34 城规则仍得到 6 小时，无回归。

### 3.6 分享链接静默换口径（诚实性改进）

**现象**：分享链接的字段白名单故意不含「我的计价 / 自选缴费基数 / 法定参数覆盖」，但这些字段恰恰决定用户看到的数字。分享者看到的是自己填的真实单价，接收方打开后看到的是本城占位单价，两个数字不同且无任何提示。

**修复**：保留隐私白名单不变，但在复制链接时若检测到上述本地输入，明确提示"链接不含你填写的计价/缴费基数，对方看到的是本城占位参数"。

这是产品伦理问题而不是安全漏洞：不泄露用户的商业数据，也不让一条"原样发给你"的链接变成另一个结论。

## 4. 审计发现（未修复，按优先级）

### 4.0 P0 — 定位与实现不一致：现在是"收入精算器"，不是"权益导航平台"

产品目标是"让劳动者知道自己该做什么、能拿什么、去哪办"，但当前实现的首页、导航与内容权重都在讲"算钱"：

| 证据 | 现状 |
|---|---|
| 首页第一屏 | 4 个 KPI：月净收入 / 年净收入 / 有效时薪 / 权益评分 |
| 导航顺序 | 总览 → 方案对比 → 税务与养老 → 权益护航 → 政策百科（权益排第 4） |
| 首页新手引导 | 三步全部在教"填工时/成本/参保"，没有"你该办哪几件事" |
| 受众措辞 | 「骑手」16 个文件、「外卖」10 个、「网约车」6 个；「工人」0 |
| 权益内容 | 民生手册 23 条，藏在「政策百科」第 6 个页签 |
| AI 提示词 | 旧版「面向灵活就业者（外卖骑手、网约车司机等）的决策助手」（2026-11-19 已改为权益导航办事助手） |
| 身份分流 | 无；整个计算模型默认"按单计价 + 自缴社保" |

这不是文案问题，是产品结构问题：用户（尤其是刚出社会的人）打开后看到的是"你的净收入"，而不是"你本周要去办的三件事"。迁移方案、目标信息架构与内容标准见 `docs/POSITIONING.md` 第 4–8 节。

### 4.1 P0 — 数据可信度是产品最大的短板

| 指标 | 数值 |
|---|---:|
| 四字段（养老/医保/最低工资/退休）官方核实 | **32 / 136（23.5%）** |
| 四字段全部官方核实的城市 | **0 / 34** |
| 四字段 0 官方核实的城市 | **20 / 34** |
| 北京 | 1/4（仅养老） |
| 上海 | **0/4** |
| 广州 / 深圳 / 成都 / 重庆 / 武汉 / 西安 / 郑州 | 3/4（退休多为 derived） |

`verify:reality` 只保证"数值落在合理区间"，不能证明"这个数字属于这座城"。当前所有城市都能算出正数，但**没有一座城市的社保四件套全部来自官方文件**。这是"打开就能信"与"结构正确"之间的真实差距。

建议：

1. 优先把 Top 10 城市（北上广深 + 成都/重庆/杭州/武汉/西安/郑州）的社保四件套做成官方核实，逐条写文号、发布日期、链接；
2. 页面顶部按城市显示"本城数据缺口：N/4 已核实"，把缺口变成一等公民；
3. 每条 sources 增加"核验日期"，让数据有保质期；
4. 对 0/4 的城市，主 KPI 默认展示"区间 + 占位参数"而不是单点数字，避免被误读为精确值。

### 4.2 P1 — 预扣税与年度汇算的文案口径不一致

`calcLaborMonthly` 是**累计预扣**语义：某月算出的应纳税额低于已预扣金额时，当月退 0，不退税（真实预扣就是这样）。但页面与洞察文案称"按年度汇算清缴口径测算"。

- 12 个月收入相同时，两者等价，所以当前 UI 看不出问题；
- 收入不均时（未来 API / MCP 直接调用会遇到），年税会高于年度汇算数，且 0 收入月份仍会获得 800 元费用减除（真实汇算无所得即无费用）。探针：9 个月 10,000 + 3 个月 0，预扣口径年税 810 元，年度汇算口径 360 元。

建议把 `withholding`（预扣）与 `annualSettlement`（汇算）拆成两个纯函数，UI 明确标注"预扣口径，汇算多退少补"；`calcLaborAnnual` 走汇算。

### 4.3 P1 — 双引擎并存带来的双倍维护面

`src/engine/{IncomeEngine,TaxEngine,BenefitEngine}.ts` 与 `src/domain/*` 各有一套公式，靠 `tests/parity/*` 锁定。迁移期这样做是对的（可回滚、可对账），但长期代价是：

- 每个口径改动要改两处 + 两套测试；
- 旧引擎的 `TaxEngine.calcLabor` 与 `domain/tax/calculator` 的减除费用逻辑已经不同（前者用累计均值判断，后者按月判断），只是在 12 个月等额时恰好等价；
- 新人容易改错边。

建议 3.5.0 完成收口：冻结旧引擎、迁移剩余调用方、删除 `src/engine` 与对应 parity 测试，保留一份金样本回归。

### 4.4 P1 — 默认成本"总额一致、明细不一致"的隐性契约

| 项目 | kernel `DEFAULT_COSTS` | Web store `DEFAULT_COSTS` |
|---|---:|---:|
| 电费 | 300 | 300 |
| 保养 | **150** | **200** |
| 保险 | **0** | **100** |
| 话费 | 100 | 100 |
| 餐费 | **1,200** | **800** |
| 罚款 | **0** | **50** |
| 折旧 | **200** | **300** |
| 其他 | **0** | **100** |
| **合计** | **1,950** | **1,950** |

总额同为 1,950，说明是刻意校准过的；但没有任何测试锁定这个等式。任何人改一侧的默认值，Web 与 CLI 的"同参数同结果"就会静默破裂——这正是 `verify:entrypoints` 想防的那类缺陷，而当前基准只覆盖广州/深圳两个点。建议把默认值收敛到单一模块，并加一条"默认成本总额一致"的测试。

### 4.5 P1 — 上帝组件

| 文件 | 行数 |
|---|---:|
| `src/layouts/MainLayout.vue` | 956 |
| `src/components/ParamSidebar.vue` | 804 |
| `src/composables/useAIChat.ts` | 693 |

这四个文件承担了导航、参数、AI 会话、全局编排，是后续迭代最容易被改坏的地方。建议按"布局 / 参数表单 / AI 会话 / store 域切片"拆分，先抽纯逻辑到 composable，再做组件拆分，避免一次性大改。

### 4.6 P2 — 多入口参数上限不一致

| 入口 | 工时上限 | 单量上限 |
|---|---:|---:|
| Web 滑块 | 14 | 60（UI） |
| kernel / ScenarioService | 20 | 200 |
| HTTP API OpenAPI | 18 | 100 |
| MCP schema | 18 | 100 |

不是 bug（各自都有校验），但"同一参数在不同入口被截断"会让 API 使用者困惑。建议在 `docs/` 里给出统一的契约表，或让 API/MCP 直接复用 kernel 的 bounds。

### 4.7 P2 — 分享链路仍会丢"我的计价"

3.6 只加了提示，没有解决"接收方看到的数字不同"。可选的下一步：

- 分享时提供两个按钮：「只分享场景（占位口径）」与「带上我的计价（明确告知对方）」；
- 或者在链接里加入一个 `pricing=placeholder` 标记，接收方页面显示"此链接使用占位单价"。

在"隐私"和"复现我的结论"之间，应该让分享者自己选，而不是替 TA 决定。

### 4.8 P2 — 供应链与浏览器覆盖

- `npm audit` 在当前镜像不可用（404），CI 没有依赖漏洞扫描。建议加 `osv-scanner` 或 Dependabot，至少每周一次。
- E2E 只跑 Chromium（桌面 + Pixel 5 视口）。目标用户多在安卓 WebView / 国产浏览器，Chromium 覆盖够用；但没有 Firefox/WebKit，对"分享链接在别人手机上打开"的承诺少一层保障。
- 部署头里有 `X-Frame-Options` / `nosniff` / `Referrer-Policy`，但没有 CSP。Vue + Naive UI 的运行时样式注入使 CSP 需要 nonce/hash 方案，建议先上 `Content-Security-Policy-Report-Only` 收集违规再收紧。

### 4.9 P2 — 路线图 2.4 的决策支持仍未落地

`ROADMAP.md` 的 2.4「决策支持」里，**双城并排对比**（API 已有 `compare`，Web 没有入口）、**租车盈亏平衡**（日单量到多少才值得租车）、**一页纸可打印摘要** 都还没有。这三项都比继续加城市更能提升"可用性"。
